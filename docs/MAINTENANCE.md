# Поддръжка: бекъп, възстановяване, достъп на админ, почистване

Кратка документация за локалната (тестова) среда в Docker. За продукция (хостинг, домейн, автоматичен бекъп) трябва да се допълни във фаза 7, когато има избран хостинг. Командите по-долу са пробвани на тази среда (20.10.2026): бекъпът е възстановен в празна помощна база и броят на редовете съвпада.

Контейнерът на базата е `db`, потребителят и базата са `b2b` (от `.env`; стойностите по подразбиране са в `docker-compose.yml`).

## 1. Бекъп на базата

Не пишете изхода на `pg_dump` с `>` в PowerShell: той променя кодировката и файлът се разваля. Правете го така (работи в PowerShell и Git Bash; в Git Bash добавете `MSYS_NO_PATHCONV=1` пред командите):

```
docker compose exec -T db pg_dump -U b2b -Fc b2b -f /tmp/b2b.dump
docker compose cp db:/tmp/b2b.dump ./b2b-2026-10-20.dump
docker compose exec -T db rm /tmp/b2b.dump
```

- Файлът съдържа всички данни: админи (хешове на пароли, криптирани 2FA секрети), клиенти, фирми, журнал. Пазете го като тайна. Файловете `*.dump` са в `.gitignore`, но най-добре го държите извън проекта.
- Томът на Docker (`naskob2b_db-data`) се губи при `docker compose down -v`. Без бекъп данните не се възстановяват.
- Ключът `TOTP_ENCRYPTION_KEY` от `.env` трябва да се пази заедно с бекъпа: без него 2FA секретите в базата не могат да се разшифроват.

## 2. Възстановяване

Първо проверявайте върху помощна база, не върху работната:

```
docker compose exec -T db createdb -U b2b b2b_restore_check
docker compose cp ./b2b-2026-10-20.dump db:/tmp/restore.dump
docker compose exec -T db pg_restore -U b2b -d b2b_restore_check --no-owner /tmp/restore.dump
docker compose exec -T db psql -U b2b -d b2b_restore_check -c "select count(*) from products"
docker compose exec -T db dropdb -U b2b b2b_restore_check
```

Истинско възстановяване (заменя работната база, спрете приложението преди това):

```
docker compose stop app
docker compose exec -T db dropdb -U b2b b2b
docker compose exec -T db createdb -U b2b b2b
docker compose exec -T db pg_restore -U b2b -d b2b --no-owner /tmp/restore.dump
docker compose start app
```

Репетиция на възстановяване върху истински хостинг още не е правена (виж `UNVERIFIED.md`).

## 3. Аварийно връщане на достъп на админ

- **Забравена парола:** http://localhost:3200/admin/forgot-password (връзката идва по имейл; в тестовата среда в Mailpit на http://localhost:8025). Ресетът променя само паролата; 2FA остава.
- **Загубено устройство за 2FA:** друг админ с роля „преглед + редакция“ нулира 2FA в раздел „Админи“ (иска негова парола и код); засегнатият настройва 2FA отново.
- **Няма друг достъпен админ:** създайте нов от терминала на сървъра:
  `npm run admin:create -- --email <имейл> --role editor` (паролата се въвежда скрито).
- **Има само един админ и е блокиран:** през базата, от човек с достъп до сървъра: `update admins set status = 'active' where email = '...'`. Препоръка: винаги поне двама активни админи с „преглед + редакция“.

## 4. Почистване на стари записи

`npm run db:cleanup` изтрива изтекли сесии, приключили прозорци за ограничаване на опитите и стари имейл токени (изтекли или използвани преди повече от 7 дни). Не пипа клиенти, админи, продукти и журнала. Безопасно е да се пуска винаги. Периодично пускане (например всеки ден) се настройва на хостинга (фаза 7).

## 5. Каталог

- Внос на моделите от `docs/products.json`: `npm run db:import-products` (повторното пускане обновява само техническите данни; цените, имената и описанията не се пипат).
- Снимки: `scripts/extract-product-images.py` (изисква PDF каталога, който не е в git).

## 6. Какво още липсва за продукция

Автоматичен бекъп по график и съхранение на друго място, мониторинг, HTTPS и заглавие HSTS, CSP за скриптове, пускане на почистването по график: всичко това е във фаза 7 и чака избор на хостинг.
